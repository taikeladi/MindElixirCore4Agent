## 1. 产品目标

基于 Mind Elixir Core（下文简称 MEC），开发一个供个人使用的思维导图编辑器，让 Codex 和 DeepseekV4 能在阅读文档后直接生成、读取和修改导图，同时保留方便的人类编辑体验。

产品方向：

- 使用 MEC 作为导图基础，优先复用现有渲染、布局和编辑功能。
- AI 需要能实际操作导图；仅输出一段大纲、图片或让用户反复手工粘贴，不足以完成最终目标。
- 主要流程是“阅读文档 → 整理结构 → 生成导图 → 人或 AI 继续修改”。
- 人类能方便地增删改节点、调整层级、拖动、展开收起、缩放和撤销。
- 视觉简洁、分支清晰，导图占据主要页面空间。
- 面向个人使用，首版优先实现本地编辑与保存。
- 源码公开不代表公开用户资料；导图存档、原始文档和模型密钥不入库。

以下状态表描述首次设计交接时的实现，当前功能以使用说明和源码为准。

## 3. 首版范围建议，尚非全部已确定需求

建议先做一个可实际使用的闭环：

1. 人或 AI 创建一张导图，浏览器立即显示。
2. AI 能读取整张导图或指定子树，并按节点 ID 修改局部内容。
3. 人工编辑和 AI 编辑使用一致的数据与提交规则，不互相覆盖。
4. 导图能保存，重新打开后内容、节点 ID 和附加信息保留。
5. 对一批 AI 修改提供整体回退能力。
6. 节点可保留来源文档、页码/章节或引用片段，便于回看原文。

首版可以由 Codex 或其他现有读取工具先完成文档阅读，再把结构化结果交给编辑器。用户尚未指定必须内置哪些 PDF、Word、网页读取器，也没有要求先实现完整知识库或 RAG 系统。

内置模型聊天侧栏、多用户协作、账号系统、复杂富文本、图形导出、跨设备同步等不应自动加入首版范围；可在主流程可用后决定。

## 4. 推荐架构：共用编辑协议，模型适配与 MEC 分离

```text
文档阅读 / 内容提取
        ↓
Codex 或 DeepseekV4
        ↓
统一的结构化编辑命令
        ↓
校验、版本检查、批量提交、持久化
        ↓
MEC 适配层与浏览器界面
        ↑
鼠标、键盘、人工编辑
```

这些是架构建议，尚未实现：

- 用 JSON 作为完整可恢复的数据格式，保留稳定节点 ID。
- AI 操作协议表达“改哪个节点、改什么”，不要求 AI 计算坐标或通过鼠标定位。
- 协议可包含 `get_document`、`get_subtree`、`apply_operations`、首次创建/导入等能力；这些名称是建议，不是 MEC 原生接口。
- `apply_operations` 建议支持添加、修改、移动、删除节点，以及批量提交。
- 对节点 ID、父子关系、目标存在性做校验；移动节点不能形成循环。
- 明确唯一提交入口和版本号，避免浏览器内存与磁盘各自修改、相互覆盖。
- 批量修改尽量一次校验并一次提交，失败时不留下半张导图。
- 编辑工具应返回执行结果、受影响节点及新版本号，让 AI 知道是否真正成功。
- 外部工具写入后，已打开的浏览器应同步更新；仅生成磁盘文件不等于完成直接编辑体验。

Codex 的接入传输可以选择 MCP、本地 API 或可调用的 CLI；新对话应依据实际可用工具确定，避免未经核实直接假定某种接入已经存在。

DeepseekV4 是用户指定的目标名称。本对话未核实其官方模型 ID、可用接口、认证方式或工具调用能力，也没有提供密钥。接入前查官方资料，保留模型适配层，不擅自替换为其他型号；模型接入信息缺失时，可先完成独立于模型的编辑协议与本地验证。

如果实施涉及 Codex 配置或工具接入，应读取当时可用的 `openai-docs` 技能并核实对应接口。现有文档没有预先决定使用某个 Codex 模型 API。

## 5. 文档整理的质量约定建议

- 导图围绕文档主题、论点和关系组织，避免机械地逐段复制原文。
- 节点标题短而明确，长说明放入备注或详情区域。
- 文档事实、AI 归纳和待确认推断在需要时能够区分。
- 尽量保存来源引用，可放入节点 `metadata`，具体字段由实现确定。
- 用户改过的文字和层级应能保留；再次要求 AI 补充时，默认局部修改。
- 不强制所有文档套同一层级模板；可根据文章、需求文档、技术说明选择结构。

## 6. 已读源码的关键结论与实现注意点

以下依据本地 5.15.1，后续升级应复核。

### 数据与渲染

- `nodeData` 是根节点，`children` 构成树；`arrows` 是独立关联线，`summaries` 是括号式总结标记。
- 节点有 `id`、`topic`、`children`、`expanded`、`note`、`metadata` 等字段。`note` 和 `metadata` 已原生定义，但不会自动生成业务编辑面板。
- 运行时会添加 `parent` 对象引用。保存应使用 `getData()` / `getDataString()`，不要直接序列化带循环引用的运行时树。
- 节点由 HTML 表示，浏览器用 CSS 排版，代码读取位置和尺寸后画 SVG 连线。
- 名为 `map-canvas` 的容器是 `div`，并非 HTML Canvas。
- 支持 `LEFT=0`、`RIGHT=1`、`SIDE=2`、`DOWN=3`；双侧模式按一级分支数量分配未指定方向的分支，不是全局最优布局算法。

### 编辑与历史记录

- 很多编辑方法接收节点 DOM 元素，完整编辑器依赖浏览器。
- 使用实例级 `findEle(id)` 定位时，收起的子树内部可能没有对应 DOM；适配层必须处理这种情况。
- 正常节点操作会更新数据/DOM并发出事件；直接改数据再 `refresh()` 不等价于完整编辑事务。
- `setNodeTopic()` 在当前实现中未发出 `operation` 事件，不能假定所有 setter 都会自动记入历史或触发保存。选择接口前检查事件行为。
- `before` 包装节点操作，支持异步判断；若自定义钩子允许操作，需要显式返回真值。不要假定它覆盖全部视图、箭头和总结操作。
- 内置撤销记录保存操作前后整图快照；AI 多条操作需要另外设计一次性撤销/事务边界。
- 单纯调用 `refresh(data)` 不会自动形成一条用户编辑历史。

### 文本格式与 AI

- `plaintextToMindElixir()` 可将缩进大纲转换为导图；`mindElixirToPlaintext()` 可反向输出。
- 适合初次生成或向 AI 展示结构，不适合作为唯一完整保存格式。
- 重新解析文本会生成新的实际节点 ID；文本 `[^ref]` 标记也不等于稳定保留原节点 ID。
- 反向文本转换不能完整保留图片、备注、任意业务元数据等所有字段。
- 流式生成时不要简单地每个 token 都全图解析、全图替换；需要节流、稳定 ID 和最终一致性设计。
- 仓库 `skills/` 中提供了集成、文本格式、流式展示等参考指南；它们不是已经运行的 AI 服务，也不代表用户已选择其中全部技术方案。

### 扩展与性能

- Markdown 通过自定义解析函数接入；原始 HTML 与解析后的 HTML 需要在应用边界处理可信性。
- `install(plugin)` 本质是将实例交给插件函数；生命周期和资源清理由集成代码妥善管理。
- 图片导出旧接口 `exportSvg()` 已标记弃用，README 推荐接入 `@zumer/snapdom`。
- 大量展开节点会增加 DOM 和布局开销，撤销快照也会增加内存占用。本项目没有完成性能基准，不要承诺具体节点容量。

## 8. 建议的新对话执行顺序

1. 阅读本交接，核对本地文件、服务状态和适用指令，保留现有全窗口编辑体验。
2. 简要明确第一版方案：数据结构、唯一写入入口、持久化位置、AI 到浏览器的通信方式。
3. 先建立保存/恢复和统一编辑命令的最小闭环，以虚构数据开发。
4. 接入 Codex 可调用的读取/编辑工具，让工具修改能立即反映到页面。
5. 核实并接入用户指定 DeepseekV4，通过同一套编辑协议操作。
6. 用一份示例文档完成“阅读 → 生成 → 人工修改 → AI 局部补充 → 保存重开”的端到端演示。

必要的验证应覆盖：稳定 ID、编辑持久化、收起分支的修改、无效命令不污染数据、人工修改后的版本冲突、批量撤销。不要仅验证“页面能画出来”。

## 9. 验收标准建议

- 浏览器中保留简洁、以导图为主的编辑页面。
- AI 能通过工具实际创建和修改导图，不要求用户搬运每次结果。
- 人工编辑后，AI 读取到的是最新内容。
- AI 局部修改不会无意重置其他分支、节点 ID 或来源信息。
- 页面刷新或应用重启后，可以恢复保存内容。
- 有一份可回看的演示文档及对应导图，用于检验内容结构和来源关系。
- Codex 和 DeepseekV4 的接入状态分别说明；没有实际完成连接时，不宣称双端已经可用。
